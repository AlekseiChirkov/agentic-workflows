# 12. Одна ветвь составной задачи и изолированное выполнение её детей

## 1. Статус и проверенное исходное состояние

**Status:** Planned contract for isolated parallel subtask execution. Updated 2026-11-06. This specification does not itself enable parallel execution or authorize publication.

В снимке `8c2fa08c18115ffcf38a1798742c41e53a2c7461` действующий [процесс выполнения](https://github.com/AlekseiChirkov/agentic-workflows/blob/8c2fa08c18115ffcf38a1798742c41e53a2c7461/workflows/spec-run.md) последователен: листы образуют цепочку ветвей, а отдельная ветвь составной задачи прямо не создаётся. [Интеграционная проверка](https://github.com/AlekseiChirkov/agentic-workflows/blob/8c2fa08c18115ffcf38a1798742c41e53a2c7461/workflows/phase-composite-validation.md) уже различает проверку детей, итоговый результат и открытые интеграционные ошибки. Это не реализация временных рабочих деревьев и параллельных работников.

[Действующая дисциплина записи](https://github.com/AlekseiChirkov/agentic-workflows/blob/8c2fa08c18115ffcf38a1798742c41e53a2c7461/rules/orchestration.md) позволяет работнику изменять собственный блок листа, но возвращает общие изменения оркестратору. В этой спецификации для нового режима все записи в `.ai/`, включая собственные блоки детей, переходят одному оркестратору. Это целевое изменение, а не описание уже установленного поведения.

Основание: ADR-0009, решения 2 и 4. Новая запись решения при реализации должна точно указать, какие положения ADR-0004, решения 3, и ADR-0005, решения 1, заменены. История прежних решений не переписывается.

## 2. Цель, границы и важные уточнения

Составная задача проверяется и рассматривается как единый результат: у неё одна постоянная рабочая ветвь и, когда публикация разрешена, один запрос на изменение. Каждый ребёнок работает на принадлежащей запуску временной ветви, проходит применимые проверки и включается в общую ветвь коммитом слияния без уплощения истории.

The goal is to reduce elapsed implementation time for one large task by concurrently running as many eligible atomic subtasks as can be proven independent. This includes direct atomic subtasks and atomic descendants of composite subtasks within one repository and task run. Dependencies, file ownership, integration gates and resource locks remain binding. A speedup, lower token use or lower cost is not guaranteed. Sequential execution retains the same quality requirements.

Устранённые неоднозначности исходной редакции:

- **«Один запрос» условен разрешением публикации.** Без `--allow-pr` нет отправки ветвей и вызовов создания запросов; при разрешении создаётся ровно один запрос на составную задачу, а не по одному на ребёнка.
- **Режим без флага остаётся последовательным.** `--parallel` без числа означает запрос двух исполнителей; `--parallel N` задаёт явный максимум. Значение 2 сохраняет исходный выбор для включённого параллельного режима.
- **Последовательное продолжение после пересечения начинается от текущей ветви составной задачи**, но ребёнок по-прежнему получает собственную временную ветвь. Он не начинает писать прямо в общую ветвь.
- **Применяется действующий тестовый режим ребёнка.** Для новой тестируемой функции или исправления поведения сохраняется RED до реализации. Для изменения без изменения поведения допустим `atomic-tests: pinned`: тесты фиксируют прежнее поведение, проходят до изменения и переходят только в `green`; тестовые доказательства фиксируются до соответствующих изменений без искусственного RED. Обоснованный `none/n-a` сохраняет допустимый один коммит. Для старого блока без `atomic-tests:`, уже имеющего `atomic-execution: in-progress`, сохраняется узкое продолжение с заметкой `pre-TDD task, TDD step skipped`, без RED задним числом. Новая или ещё не начатая задача не получает такое исключение. Основания — [каноническое состояние](https://github.com/AlekseiChirkov/agentic-workflows/blob/8c2fa08c18115ffcf38a1798742c41e53a2c7461/rules/workflow-globals.md) и [правила коммитов](https://github.com/AlekseiChirkov/agentic-workflows/blob/8c2fa08c18115ffcf38a1798742c41e53a2c7461/rules/git-flow.md).

Эти уточнения задают согласованный целевой текст, но не заменяют требуемую запись изменения поведения при реализации.

Out of scope: concurrent independent top-level tasks or specifications; parallel discovery; multiple repositories; parallel ordinary single-session execution; a separate integration branch; state tool 07; and automatic merging of owner pull requests. Parallel atomic descendants within one large task are in scope, including across composite boundaries.

## 4. Термины и инварианты

**Составная задача** — существующий разрешённый тип задачи с детьми и отдельными интеграционными критериями. **Волна** — ограниченный набор одновременно запущенных независимых детей; это единица планирования, не дополнительная ветвь. **Временная ветвь ребёнка** — принадлежащая конкретному запуску ветвь с записанными основанием и вершиной. **Включение** — проверенное слияние точной вершины ребёнка в ветвь составной задачи.

Обязательные инварианты:

1. Верхнеуровневые задачи сохраняют последовательную цепочку. Следующая начинается только от проверенной вершины предыдущей.
2. У составной задачи одна ветвь. У ребёнка нет отдельного публичного запроса на изменение.
3. Каждый ребёнок работает в изолированном рабочем дереве; изменением ссылок, коммитами и общими файлами владеет оркестратор.
4. Содержимое `.ai/` не записывается работниками нового режима. Пакеты контекста — доступные только для чтения снимки, результаты — сообщения и частные артефакты работника.
5. Перед новой реализацией сохраняются применимые тестовые доказательства: RED для нового/исправляемого поведения либо `pinned` для фиксации неизменяемого поведения. Законный `none/n-a` и узкая совместимость уже начатой старой задачи не порождают выдуманного RED. Слияние не удаляет имеющуюся историю.
6. Успешная проверка ребёнка не доказывает успешную интеграцию. После слияния проверяется фактический объединённый результат.
7. Чистое текстовое слияние не доказывает независимость: изменение общего интерфейса может конфликтовать без общих файлов.
8. Удаление ветвей и рабочих деревьев допускается только после доказанного включения и сохранения результатов; неудобный конфликт не оправдывает удаление работы.
9. Повторное сообщение, поздний результат и перезапуск оркестратора не создают второй коммит слияния, второй запрос или дополнительную неучтённую попытку исправления.
10. Неизвестная возможность среды и неопределённая независимость не трактуются как разрешение параллельности.

## 5. Нормативные требования

REQ-01–REQ-05 сохранены из исходных дополнений; остальные идентификаторы формализуют ранее ненумерованные критерии.

- **REQ-01. Контекст и запись.** Каждому ребёнку выдаётся неизменяемый пакет 14 и свежая ограниченная проекция без переписок соседей. Все предложения изменения состояния из конвертов 15 проверяет и последовательно применяет оркестратор; работники не публикуют устаревшие подтверждения.
- **REQ-02. Учёт.** Запросы детей, повторы, проверки и записи кэша учитываются однократно по 05. Общее время ожидания показывается отдельно от суммы времени работников. Ускорение не объявляется уменьшением стоимости.
- **REQ-03. История и интеграция.** Сохраняется применимый порядок тестов и реализации. До слияния проверяются пересечения и доказательства ребёнка; на фактическом объединённом дереве выполняются нужные интеграционные проверки. Провал слияния или проверки не создаёт проверенную составную задачу.
- **REQ-04. Риск и исправления.** Применяется 16 к ребёнку и общей области; после значимых изменений подтверждения аннулируются. Политика 19 допускается только для изолированного подходящего дефекта. Опасный общий контракт или критическое замечание прекращают новую отправку работ, сохраняют результаты и переходят к действующей процедуре решения.
- **REQ-05. Независимость и возможности.** Доказательства поступают из 20 и применимого классификатора. Требуются отсутствие пересечения файлов, общего изменяемого контракта/схемы, ребра зависимости и ограничения порядка. Разрешения роли/модели не ослабляются. Неподдерживаемый явный параллельный запрос отклоняется; обычный режим остаётся последовательным.
- **REQ-06. Ветвление.** Ветвь составной задачи создаётся от проверенной вершины предыдущей верхнеуровневой задачи; для первой — от разрешённой исходной ветви. Каждый ребёнок получает временную ветвь от зафиксированной вершины составной задачи.
- **REQ-07. Слияние и сохранение.** Дети включаются с `--no-ff`, без уплощения коммитов. Сохраняются коммиты тестов и реализации; удаление допускается только с подтверждением владения и точного включения по 06.
- **REQ-08. Публикация.** В режиме разрешённой публикации составная задача имеет ровно один запрос с одной строкой позиции в цепочке и разделом каждого ребёнка. Без разрешения публикации создаётся только локальный результат. Автоматическое слияние запроса не входит в полномочия.
- **REQ-09. Описание плана.** Декомпозиция записывает `Parallel-safe: yes | no`, точные файлы/интерфейсы, основания независимости и порядок интеграции в `plan.md → ## Decomposition Decisions`. Неопределённость равна `no` до её разрешения.
- **REQ-10. Ограничение параллельности.** Число одновременно активных детей не превышает выбранное положительное целое N. Для N > 1 нужны фактические `worktrees: yes` и `concurrent-sub-agents: yes`; одного `sub-agents: yes` недостаточно.
- **REQ-11. Повторная проверка пересечения.** До запуска, по мере получения фактических путей и непосредственно перед слиянием проверяются пересечения с запланированными, выполняемыми, завершёнными и уже включёнными детьми соответствующей волны. Обнаружение пересечения отключает дальнейшее параллельное выполнение этой составной задачи и запускает безопасную сериализацию.
- **REQ-12. Единственная итоговая проверка.** После включения последнего ребёнка оркестратор запускает `/phase-composite-validation` — после миграции `composite-validation` — на общей ветви. Сигнал закрытия ребёнка не запускает второй экземпляр проверки в его рабочем дереве.
- **REQ-13. Восстановление.** Журнал связывает ребёнка, рабочее дерево, основание, текущую вершину, конверт, операцию слияния и проверку. После прерывания оркестратор сверяет реальный репозиторий; не полагается только на последнее записанное слово статуса.
- **REQ-14. Последовательное продолжение.** При пересечении остановить новые отправки, сохранить активную работу и выполнить оставшиеся дети последовательно свежими исполнителями от актуальной общей базы через временные ветви. Пригодные доказательства переиспользуются только после проверки актуальности; неподтверждённый результат не подмешивается автоматически.
- **REQ-15. Регрессия и эквивалентность.** Автономные сценарии подтверждают одинаковые критерии, ограничения и итоговое поведение при N = 1 и N = 2; разрешённые живые эталоны сравниваются отдельно по 09. Нормализация допускает разные служебные идентификаторы, но не скрывает отсутствующее доказательство.
- **REQ-16. Миграция.** Правила, процессы, состояние, ограничения и документация изменяются согласованно; принятая запись решения фиксирует заменённые положения. Активные задачи прежней модели не переводятся незаметно в новую при возобновлении.

## 6. Интерфейс режима и предварительная проверка

### 6.1. Разбор параметра

| Обращение | Значение |
|---|---|
| `/spec-run ...` | Последовательное выполнение, N = 1 |
| `/spec-run ... --parallel` | Явный запрос параллельности с исходным значением N = 2 |
| `/spec-run ... --parallel 1` | Последовательный путь новой модели составной задачи |
| `/spec-run ... --parallel N` | Явный максимум N; положительное целое |
| Ноль, отрицательное, дробное, нечисловое значение | Ошибка до создания ветвей и запуска работников |

Конфигурационный предел может ограничивать параллельность в рамках уже выбранного режима, но не должен молча превращать отсутствие флага в параллельный запуск. Если явный запрос не поддерживается, возвращается объяснимый отказ с возможностью выбрать последовательный режим. Не следует молча заменять N > 1 на 1 и сообщать, что запрос выполнен.

### 6.2. Проверки до первого изменения

Оркестратор проверяет репозиторий и разрешённую рабочую директорию; отсутствие конфликтующих отслеживаемых изменений; политику знаний `.ai/`; готовность предыдущей верхнеуровневой задачи; ревизию плана; независимость; свободные имена ветвей и деревьев; достаточность возможностей среды; соответствие моделей/усилия; разрешение публикации при необходимости.

Наличие механизма рабочих деревьев не доказывает способность безопасно запускать независимые подагенты. Описанные возможности должны быть подтверждены адаптером установленной версии. Механизм ограничения числа работников также проверяется, а не выводится из мощности модели.

Неотслеживаемые пользовательские файлы сохраняются по действующей политике. Создание рабочего дерева не даёт права удалять их ради чистоты.

## 7. План независимости

Для каждого ребёнка требуется запись:

| Поле | Содержание |
|---|---|
| `child_id`, `composite_id` | Канонические локальные идентификаторы |
| `target_files` | Конкретные предполагаемые пути; переименование указывает обе стороны |
| `interfaces` | Производимые/потребляемые контракты и схемы, включая общие конфигурации |
| `dependencies` | Точные предшественники с условиями готовности |
| `parallel_safe` | `yes` или `no` |
| `independence_evidence` | Основания по всем четырём условиям, хэш плана и источников |
| `integration_order` | Детерминированный разрешённый порядок включения |
| `integration_checks` | Общие критерии, проверки и владелец |
| `packet_digest` | Ссылка на пакет 14; окончательный пакет формируется для фактической базы |

Разные исходные файлы недостаточны: два ребёнка могут менять одну схему через генератор и потребителя, одну библиотечную зависимость через разные модули, глобальную конфигурацию либо один контракт ошибок. Такие изменения не запускаются параллельно без доказанной независимости.

Фактический набор путей берётся из разницы ребёнка с сохранённой базой, а не только из сообщения работника. Учитываются новые и удалённые файлы, переименования, генерируемые артефакты и метаданные зависимостей. Выход за согласованный набор вызывает проверку области до слияния.

Дети с `parallel_safe: no` выполняются отдельными последовательными шагами; их нельзя вставлять внутрь активной волны только потому, что есть свободное место.

## 8. Ветви, рабочие деревья и роли

### 8.1. Имена и владение

Имя ветви составной задачи следует действующему предметному формату `<type>/<feature-slug>`. Временная ветвь — `<composite-branch>--<child-slug>`. Подстроки `T-XX`, номера спецификаций и названия каталога задачи в имена не добавляются. Коллизия разрешается предметным уточнением либо проверенным возобновлением собственной ветви, а не случайным использованием чужой.

Журнал владения записывает идентификаторы репозитория и рабочего дерева, запуск, ребёнка, имя ветви, начальный хэш, текущую известную вершину и путь дерева. Одного совпадения имени недостаточно для изменения или удаления.

### 8.2. Действия работников

Исполнитель меняет код и тесты только своего дерева и передаёт доказательства. Оркестратор делает коммиты и общие записи. Проверяющий получает контракт, необходимые тесты и фактическую разницу; он не наследует переписку исполнителя как единственный источник понимания.

In the new parallel mode, test preparation and implementation use distinct workflow agents. The coordinator transfers the verified test checkpoint, test mode, commands, observed RED or pinned result and frozen-test restrictions to the implementation agent. This supersedes the existing same-agent RED-to-GREEN rule for this mode; implementation must record the decision and update all affected rules. A separate validation agent independently reviews the resulting revision. Sequential rework uses fresh agents and verified evidence.

Доступное только для чтения `.ai/` или отдельный пакет контекста не считается системно защищённым только из-за текста инструкции: документация адаптера отдельно указывает, обеспечивается ли запрет разрешениями среды или дисциплиной ролей. Работнику не выдаётся общая запись как удобство параллельного режима.

## 9. Порядок выполнения

### 9.1. Создание составной задачи

1. Проверить все предварительные условия и закрепить ревизию плана.
2. Создать одну ветвь от проверенной верхнеуровневой базы либо доказанно восстановить её.
3. Зафиксировать исходную вершину и модель ветвления в журнале; не создавать отдельную интеграционную ветвь.
4. Подготовить последовательные шаги и независимые волны по графу зависимостей.

### 9.2. Отправка ребёнка

1. Повторно проверить готовность зависимостей и актуальность оснований независимости.
2. Создать принадлежащие запуску временную ветвь и дерево от зафиксированной текущей общей базы. Дети одной волны обычно имеют одну базу; конкретная база записывается для каждого.
3. Сформировать пакет 14 с точной базой, критериями, запретами, командами тестов, интеграционными рисками и правилами отчётов.
4. Reserve a leaf slot within N and a task coordinator identity; dispatch each applicable atomic workflow to a distinct workflow agent under section 17.
5. Получать только значимые конверты 15; не перечитывать полностью всё состояние при каждом отсутствии нового события.
6. Определить применимый тестовый режим. Для новой тестируемой функции/исправления проверить RED и выполнить коммит тестов до разрешения реализации. Для допустимого изменения без смены поведения проверить `pinned`, зафиксировать проходящие тесты до изменения и затем разрешить переход только в `green`. Проверить итог GREEN и выполнить соответствующий коммит реализации. Законный `n-a` и старый уже начатый блок без `atomic-tests:` обрабатываются отдельными действующими путями: во втором случае сохраняется точная заметка о прежнем формате, но RED не придумывается задним числом. Удаление поля или подмена режима для новой работы запрещены.
7. Dispatch atomic validation to a fresh independent workflow agent. Do not admit the result for integration before validation succeeds.

### 9.3. Включение проверенного ребёнка

Integration uses a deterministic dependency-compatible order from the plan, not message arrival order. The plan must not place a dependent before its prerequisite. Independent ready leaves may refill available slots without waiting for an entire wave; shared writes and merges remain serialized.

1. Проверить идентичность дерева, ветви, исходной базы, текущей вершины ребёнка, конверта и независимого подтверждения.
2. Сравнить фактические изменения с планом, детьми волны и уже включёнными изменениями. Проверить также общие интерфейсы и инварианты.
3. Проверить свежесть пакета и подтверждения по 14/16. Изменившиеся входы требуют расширения проверки; одинаковое имя ветви или один хэш коммита недостаточны.
4. Зафиксировать намерение слияния с ожидаемой старой вершиной общей ветви и точной вершиной ребёнка.
5. Подготовить слияние без уплощения истории. Если используется промежуточное дерево до коммита, оно рассматривается как отдельный фактический набор входов, а не как уже принятый результат.
6. При конфликте сохранить состояние и доказательства; не применять принудительный сброс, выбор «всегда нашей/их версии» и автоматическое повторение.
7. На полученном объединённом дереве выполнить затронутые детерминированные и независимые проверки по 16. Проверки ребёнка не заменяют этот шаг.
8. Зафиксировать коммит слияния с `--no-ff`; убедиться, что дерево коммита совпадает с проверенным. Если содержимое изменилось, повторить затронутую проверку.
9. Сохранить хэш слияния, его родителей, фактическое дерево, подтверждения и состояние операции. Только после этого результат считается включённым.

Если выбранный безопасный механизм создаёт коммит до интеграционных проверок, журнал явно различает «коммит создан» и «включение принято». Провал проверки сохраняет коммит для восстановления, но не присваивает проверенное состояние и не разрешает зависимые задачи.

### 9.4. Завершение составной задачи

После принятия всех включений оркестратор на общей ветви вызывает единственную итоговую интеграционную проверку. Она охватывает интеграционные критерии описания составной задачи, объединение фактически изменённых областей, общие инварианты и границы.

Только успешное подтверждение на актуальном результате разрешает `integration-validation: complete` и перевод строки составной задачи в `reviewed`. Завершённые дети при проваленной интеграции не позволяют закрыть составную задачу.

Вызов из закрытия последнего ребёнка становится сигналом готовности оркестратору, а не независимым повторным запуском внутри дочернего дерева. Привязка операции к общей вершине и хэшу критериев предотвращает дубли.

## 10. Пересечение и переход к последовательному исполнению

Обнаружение пересечения — изменение исходного предположения независимости, а не разрешение автоматически выбирать версию файлов.

1. Пометить параллельную отправку этой составной задачи остановленной; новые дети не запускаются.
2. Сохранить фактические пути, общий контракт и причину пересечения. Не скрывать его после успешного текстового слияния.
3. Уже работающим детям передать безопасную остановку на ближайшем предусмотренном рубеже. Не удалять их деревья, ветви, частичные тесты и отчёты.
4. Зафиксировать все полученные конверты как ожидающие решения; поздний отчёт не применяется автоматически к новой базе.
5. Разделить результаты: уже включённые и подтверждённые; завершённые, но ещё не включённые; активные/частичные; не начатые. Ни одна категория не подразумевает автоматического принятия.
6. Проверить, можно ли сохранить уже включённый результат без изменения контракта. При опасном общем дефекте остановить дальнейшую интеграцию и перейти к действующей процедуре решения.
7. Для оставшихся детей построить последовательный порядок. Каждый новый или требующий переработки ребёнок получает свежего исполнителя и новую принадлежащую запуску ветвь от актуальной общей базы.
8. Ранее завершённый результат может стать доказательством и исходным материалом. Его принятие без переработки допустимо только при совпадении значимых входов и повторной проверке интеграции. Перенос изменений не отменяет применимый порядок тестов.
9. Если на новой базе воспроизводящий тест уже проходит, не фабриковать RED: уточнить покрытие и оставшуюся цель по действующей процедуре изменения плана. Это не превращает новую функцию или исправление поведения в `pinned`; данный режим остаётся допустим только для фиксации сохраняемого существующего поведения.
10. Сохранять предыдущие ветви до доказанного включения либо отдельного разрешённого решения об их судьбе. Не переписывать историю, чтобы сделать прерванную волну похожей на успешную.

Переход к последовательности остаётся активным до завершения этой составной задачи, если отдельно согласованное перепланирование не установит новый безопасный контракт. Он не запускает бесконечную череду «параллельно — конфликт — повтор».

## 11. Состояние, конверты и журнал восстановления

Существующие канонические статусы сохраняются. Техническое состояние слияния не подменяет `atomic-validation` и `integration-validation`.

Минимальные аддитивные сведения журнала:

| Группа | Сведения |
|---|---|
| Запуск | `run_id`, версия модели ветвления, идентификатор репозитория, хэш плана |
| Составная задача | Идентификатор, общая ветвь, верхнеуровневая база, фактическая общая вершина |
| Ребёнок | Идентификатор, ветвь/дерево, исходный хэш, последняя вершина, фактические пути |
| Контекст | Хэш пакета, критериев, тестов и значимых интерфейсов |
| Параллельность | Запрошенный и фактический N, номер волны, причина последовательного продолжения |
| Проверка | Идентификаторы конвертов, независимых подтверждений и открытых замечаний |
| Включение | Идентификатор операции, ожидаемые родительские вершины, хэш слияния, фактическое дерево, результат проверок |
| Очистка | Доказательство владения/включения, освобождения дерева и отсутствия новой работы |
| Исправления | Ссылка на эпизод и счётчики 19; перезапуск не создаёт новый лимит |

Для одного слияния журнал различает хотя бы намерение, начатую операцию, созданный коммит, проверенное принятие и завершённую уборку. Это логические стадии журнала, а не новый словарь статусов задачи. Изменение состояния и обновление ссылок не образуют общей файловой транзакции; восстановление обязано сопоставлять обе стороны.

У двух одновременно отправленных детей может быть один исходный хэш общего состояния. Применение первого результата делает исходную ревизию второго старой, даже если его собственная работа остаётся правильной. Оркестратор не переписывает старый конверт и не применяет его старый патч: он сверяет актуальные целевые поля, контракт, дерево и доказательства, затем при сохранении предусловий формирует новое производное предложение к текущей ревизии с отдельным `proposal_id` и ссылкой `original_event_id`. Исходный `event_id` и его хэш остаются неизменными. Такая согласованная переподготовка не является новым исполнением, новой попыткой исправления или второй оплачиваемой единицей; история связывает исходное сообщение и единственное принятое изменение. Конфликт значимых полей требует решения, а не механического переноса.

### 11.1. Возобновление

- Если намерение записано, а изменений нет, повторить проверку предшествующих условий до исполнения.
- Если слияние прервано конфликтом, сохранить конфликт и не начинать другой merge поверх него.
- Если коммит создан, а подтверждение не записано, проверить его точных родителей, дерево и фактические доказательства; не создавать второй коммит автоматически.
- Если состояние помечено принятым, но общая вершина/проверенные входы изменились, признать подтверждение устаревшим и проверить соответствующую область.
- Если пришёл повторный конверт, сравнить идентификатор и хэш содержания; одинаковый уже применённый результат не повторять, различающийся — отклонить как конфликт.
- Если запрос на изменение уже существует, проверить его репозиторий, исходную и целевую ветви, принадлежность запуску; обновить в пределах разрешения вместо создания второго.
- Если работник после перезапуска неизвестен, сначала проверить его существование и дерево. Не запускать замену поверх живой работы.

## 12. Ошибки и исправления

| Ситуация | Действие |
|---|---|
| Не хватает возможности среды | Явный параллельный запрос отклонён; последовательный путь доступен отдельно |
| Независимость не доказана | Ребёнок выполняется последовательно |
| Выход за целевые файлы или изменение общего контракта | Остановить отправку/включение, сохранить доказательства и пересмотреть область |
| Независимая проверка ребёнка неуспешна | Сохранить остановку по умолчанию; применять 19 только при явно включённой допустимой политике |
| Конфликт слияния | Сохранить ветви и конфликт; не разрешать автоматически и не объявлять включение успешным |
| Общий результат нарушает критерий | Составная задача остаётся непроверенной; использовать существующий процесс интеграционных замечаний и исправляющих детей |
| Критическое нарушение инварианта, безопасности или согласованной архитектуры | Прекратить новые отправки и перейти к предусмотренному решению; не размножать автономные попытки |
| Ошибка записи/учёта вывода | Сохранить факт неопределённости; не повторять изменение ради получения красивого вывода |
| Превышение лимита провайдера | Сохранить работу, остановить новые вызовы; не менять аккаунт для обхода ограничения |
| Сбой уборки | Оставить ветвь/дерево и сообщить причину; успешный результат не требует рискованного удаления |

Интеграционные исправляющие дети создаются по действующему протоколу решений: в интерактивном режиме — по решению пользователя; в уже разрешённом автономном режиме — с предусмотренной автоматической классификацией `critical`/`important`/`optional`. Это не отменяет специальных жёстких остановок при нарушении намерения, архитектуры или инвариантов. Создание исправляющего ребёнка не означает его молчаливого запуска в оставшейся параллельной волне.

Политика 19 сохраняет максимум одну местную и одну явно разрешённую усиленную попытку на эпизод; место попытки резервируется до запуска. Неопределённый уже отправленный запуск не считается бесплатным повтором. Сериализация, смена дерева и новый исполнитель не обнуляют историю.

## 13. Публикация и очистка

### 13.1. Один запрос на изменение

После успешной общей проверки и при действующем `--allow-pr` публикуется общая ветвь и создаётся/обновляется один запрос. Его целевая ветвь — предыдущая верхнеуровневая ветвь либо начальная база для первой задачи. Временные дочерние ветви отдельно не публикуются ради создания запросов.

Содержание включает предметную цель, общий результат, одну строку позиции в цепочке, по каждому ребёнку — цель, критерии и доказательства тестирования, включая хэш коммита тестов там, где они требуются. Используются предметные названия детей, а не `T-XX`, номера спецификаций, ссылки на `.ai/` и внутренние названия процессов: соответствие локальным идентификаторам хранится в состоянии. Текст объясняет порядок тестов обычным языком без запрещённого внутреннего жаргона.

Наличие чернового запроса само по себе не является техническим запретом его слияния. Пользователь выбирает окончательное слияние; агент сохраняет действующие ограничения 06 и не выполняет `gh pr merge`.

### 13.2. Очистка временной работы

До удаления проверяются точная принадлежность ветви, совпадение сохранённой вершины, факт её включения в принятую общую историю, отсутствие активного работника и несохранённых изменений. Сначала безопасно освобождается рабочее дерево; затем удаляется только доказанно принадлежащая запуску временная ветвь разрешённым способом.

Если указатель ветви переместился после включения, удаление запрещено до новой проверки. Если доказательство отсутствует, ветвь сохраняется. Принудительные удаления, `reset --hard` и `clean` не используются как средство уборки.

## 14. Измерение и сравнение режимов

В журнале сохраняются `parallel: N` для запуска и `wave: k` для дочерних шагов, а также фактическое число активных работников и причина снижения параллельности. Телеметрия 05 связывает каждую попытку и проверку с ребёнком, не дублируя её в сумме составной задачи.

Отчёт показывает общее прошедшее время, сумму длительностей работников, время оркестратора/интеграции, число повторных проверок, объёмы контекста и наблюдаемые чтения/записи кэша. Сумму длительностей нельзя прибавить к общему времени как ещё один расход времени пользователя.

Параллельный режим может быть быстрее и дороже. Сравнение по 09 использует одинаковые исходные задачи и независимые критерии, включая дефекты интеграции. Нормализованные артефакты N = 1 и N = 2 должны совпадать по смысловым обязательствам, а не обязательно по каждому хэшу или моменту записи.

## 15. Критерии приёмки

- [ ] **AC-01** (REQ-01, REQ-02): перемежающиеся события двух детей не смешивают контекст; общие изменения применяются последовательно; запросы учитываются однократно, сумма времени работников не становится временем ожидания.
- [ ] **AC-02** (REQ-03, REQ-04): конфликты, изменённые интерфейсы и неуспешные проверки сохраняют историю, аннулируют устаревшие подтверждения и не закрывают составную задачу.
- [ ] **AC-03** (REQ-05): неподдерживаемая среда, пересекающиеся пути и общий изменяемый контракт не запускают параллельную волну. Смысловые обязательства последовательного и параллельного результатов совпадают; платная проверка отдельно разрешается.
- [ ] **AC-04** (REQ-06, REQ-07): у задачи одна общая ветвь, каждый ребёнок имеет временную ветвь от записанной базы, слияние сохраняет родительские связи и применимые тестовые коммиты. Поддельное владение или несовпадающая вершина не позволяют удалить ветвь.
- [ ] **AC-05** (REQ-08): без `--allow-pr` отсутствуют отправки и команды создания запросов; с разрешением создаётся ровно один запрос; повтор/возобновление не создаёт дубликат, внутренние идентификаторы не попадают в публичный текст.
- [ ] **AC-06** (REQ-09, REQ-10): план содержит доказательства всех условий независимости; число активных детей не превышает N; неправильный N отклонён до эффектов; отсутствие флага остаётся последовательным.

## 17. Parallel atomic workflows across the task tree

### 17.1. Source and scope

The owner clarified on 2026-11-06 (translated from Russian): execute eligible atomic subtasks of one large task in parallel to shorten implementation time; give each atomic subtask its own coordinating agent and each atomic workflow a separate agent. Analysis and test preparation, implementation, and validation are examples of distinct workflows. The [example task](../tasks/todo/task-06-1-test-suite-runtime/plan.md) is planning evidence, not authorization to change or run it.

The current runner explicitly executes subtasks sequentially and uses one implementer for test and implementation checkpoints ([dependency ordering](../../workflows/spec-run.md#L163), [handoff](../../workflows/spec-run.md#L208), [parallelism prohibition](../../workflows/spec-run.md#L367)). Atomic execution orders test preparation, implementation and finalization ([execution](../../workflows/phase-atomic-execution.md#L100)); atomic validation orders check, proposals and close ([validation](../../workflows/phase-atomic-validation.md#L73)). This section defines a future replacement for those runner rules, not current behavior.

### 17.2. Scheduler and ownership requirements

- **REQ-17. Task tree.** WHEN an authorized parallel run processes a large task, THE SYSTEM SHALL build one dependency graph of its atomic leaves, including descendants of composite nodes and leaves directly under the task. Composite nodes remain containers and integration gates, not atomic implementation jobs. Independent top-level task runs remain sequential.
- **REQ-18. Admission.** WHEN a leaf is considered for dispatch, THE SYSTEM SHALL admit it only after every declared prerequisite is integrated and reviewed, enclosing gates and other applicable prerequisites permit execution, and its file, interface and resource independence from every active leaf is established. A composite prerequisite is satisfied only after its children and composite integration validation pass.
- **REQ-19. File exclusion.** WHILE a leaf holds its write reservation, THE SYSTEM SHALL prevent another active leaf from writing any of the same normalized repository paths, including test, configuration, generated, deleted and both sides of renamed files. A directory or glob that cannot be resolved to a complete stable set is an overlapping reservation. Distinct worktrees do not waive this exclusion; root-owned shared-state updates remain sequential under REQ-01.
- **REQ-20. Leaf coordination.** WHEN an eligible leaf starts, THE SYSTEM SHALL assign it a dedicated task-coordinator sub-agent that owns its atomic execution and validation sequence and reports to the root orchestrator; it shall not coordinate another leaf concurrently. The root remains the sole writer of shared state and owner of git operations.
- **REQ-21. Workflow agent isolation.** WHEN an applicable atomic workflow is invoked for a leaf, THE SYSTEM SHALL dispatch it to a fresh workflow sub-agent dedicated to that invocation. Atomic execution (/phase-atomic-execution), test analysis/preparation (/pae-tests), implementation (/pae-implement), finalization (/pae-finalize), atomic validation (/phase-atomic-validation), and its applicable child workflows (/pav-check, /pav-propose and /pav-close) each have a distinct fresh agent identity, also distinct from the leaf coordinator and root. Phase agents coordinate their ordered child workflow invocations; the root mediates dispatch if necessary. Finalization and close propose state deltas for the root; neither workflow workers nor leaf coordinators directly write shared .ai/ state or perform root-owned git operations.
- **REQ-22. Verified handoff.** WHEN a workflow completes, THE SYSTEM SHALL pass the next workflow an immutable, minimally scoped handoff containing leaf and attempt identities, base and exact candidate tree/commit, task contract and applicable acceptance criteria, allowed paths, test mode, commands, observed results and artifact digests. The implementation agent receives verified frozen RED or pinned evidence before implementation; the validation agent receives implementation and test evidence independently. A failed, missing, stale or mismatched handoff blocks its dependent stage.
- **REQ-23. Limits and refill.** WHILE parallel mode is active, THE SYSTEM SHALL cap active leaves at N, separately count task coordinators and workflow agents against actual platform agent capacity, and dispatch another ready independent leaf when a slot and all required locks are available. A leaf retains its slot and reservations through atomic validation and until its result is integrated or safely withdrawn. Record requested and effective limits and capacity constraints.
- **REQ-24. Failure isolation.** IF a leaf fails or is blocked, THEN THE SYSTEM SHALL block its descendants and dependent joins, retain its work and evidence, and allow unrelated eligible leaves to continue when no shared safety invariant, resource lock or critical defect requires a broader stop. Existing conflict handling in section 10 applies when asserted independence is disproved.
- **REQ-25. Capability preflight.** BEFORE creating branches or dispatching in this mode, THE SYSTEM SHALL verify worktree isolation, concurrent sub-agents, agent messaging, and the ability to run dedicated coordinators and distinct workflow agents under available delegation permissions. If nested delegation is unavailable, root-mediated flat dispatch is permitted only if it preserves the same identities, sequence, handoffs and ownership; otherwise reject the explicit parallel request with the missing capability and perform no partial dispatch.
- **REQ-26. Completion and measurement.** WHEN all leaves and composite gates complete, THE SYSTEM SHALL verify the integrated task result against the parent contract on the final tree, record the verdict, and report wall time, active-leaf concurrency, worker time, integration/rework time and conflicts separately. Compare sequential and parallel runs only on comparable inputs and quality gates; measured acceleration is evidence, not an unconditional acceptance guarantee.
- **REQ-27. Recovery.** WHEN a run resumes, THE SYSTEM SHALL reconcile each leaf coordinator, workflow invocation, attempt, reservation, candidate tree, handoff, dependency and integration receipt against actual live agents and repository state before redispatch. Never duplicate a live invocation, release a reservation held by a live writer, reuse a stale validation, or lose partial work.

### 17.3. Execution and integration contract

The root expands the task tree into a DAG, preserves composite joins, checks the versioned plan and reserves file and resource ownership before dispatch. A ready leaf gets its own isolated branch and worktree, a coordinator, and a bounded sequence of workflow agents. The coordinator directs phase sequence and returns evidence; it does not mutate shared state or git. The root may mediate workflow-agent creation when nested spawning is unavailable. An active leaf runs from reservation through integrated acceptance or safe withdrawal; N limits leaves, not the total number of agents. Platform capacity includes the root, coordinators and active workflow agents; report any smaller effective concurrency.

For testable new behavior, a test agent produces RED evidence; the root verifies and commits the test checkpoint; a fresh implementation agent receives that checkpoint and produces GREEN; the root verifies and commits implementation. For permitted characterization, transfer pinned evidence instead. Documented n-a and legacy in-progress paths remain applicable without invented RED evidence. A fresh atomic-execution phase agent coordinates test preparation, implementation and execution finalization, each dispatched to a distinct agent. After execution finalization, a fresh independent validation phase agent coordinates its ordered check, proposal and close workflows, each dispatched to a distinct agent when applicable. The root applies validated state proposals in order. No stage starts until its predecessor has successfully handed off. Validation failure cannot close the leaf.

A leaf branches from an integrated tree containing all reviewed prerequisites. For nested composites, the root integrates leaves into their owning composite branch in deterministic dependency-compatible order and runs that composite single integration gate before integrating its branch into its parent. Direct leaves integrate into the parent task branch. The parent final verification is separate from each composite gate. Cross-boundary leaves may run together only when dependencies and ownership permit it; no dependent leaf starts on an unintegrated candidate. A dependency outside the owning composite becomes usable only after its verified result is integrated into an ancestor branch and the owning composite branch incorporates that exact verified ancestor revision. If the prerequisite is inside another composite, first complete and integrate that composite gate; do not copy unintegrated leaf changes across branches. Revalidate affected evidence after incorporating ancestor changes. Existing no-fast-forward history, single-writer, recovery, publication and conflict rules remain in force.

If a worker requests or is observed to change a path outside its reservation, stop its writes and new admissions involving the affected set; preserve candidate trees and compare actual paths before integration. If overlap or a common-contract conflict invalidates independence, apply section 10 conservative stop and serialization for the affected task scope. Release a path only after integration or confirmed worker termination and preservation of its work. Read-only analysis does not acquire a write reservation and cannot be treated as completed implementation. Host-exclusive checks, benchmarks and resource locks are separate from file reservations and apply globally.

### 17.4. Example and assumptions

The example plan identifies the baseline as a prerequisite and final integration and performance work as joins. It lists four candidate lanes after the baseline, but the guard, identity, timing and lifecycle leaf descriptions all name scripts/validate-contracts.sh as a target. These leaves therefore cannot hold concurrent write reservations under REQ-19, even in separate worktrees. A revised plan may permit concurrency only after establishing complete, disjoint actual write sets and independent interfaces; otherwise they run sequentially. This example does not claim that the current task has four parallel-writable leaves.

Assumptions: the existing explicit --parallel opt-in and N=2 default remain unchanged; the requested parallelism is inside one task. The coordinator and fresh-workflow-agent model applies to the new mode and requires a capability-aware adapter. No migration of an active task is implied. The present same-agent test handoff must be replaced for this mode while retaining frozen-test guarantees.
