# 07. Отложенная спецификация инструмента безопасного изменения состояния

## 1. Статус и основание

**Работа не запланирована.** Этот документ сохраняет и уточняет проект будущего инструмента для `## Subtask Progress`. Он не разрешает внедрение, не переводит работу в текущий план и не делает её обязательным условием остальных улучшений.

Основание — ADR-0009, решение 5: пока агенты редактируют состояние существующими средствами. Основанием для отдельного планирования могут стать подтверждённые повреждения блоков, выявленные `scripts/validate-task.sh`, и решение владельца задачи. Само наличие подробной спецификации не является таким решением.

Проверенный снимок проекта: `8c2fa08c18115ffcf38a1798742c41e53a2c7461`, 2026-10-28. В [действующем контракте состояния](https://github.com/AlekseiChirkov/agentic-workflows/blob/8c2fa08c18115ffcf38a1798742c41e53a2c7461/rules/workflow-globals.md) прогресс хранится в родительском `state.md`. [Текущая дисциплина записи](https://github.com/AlekseiChirkov/agentic-workflows/blob/8c2fa08c18115ffcf38a1798742c41e53a2c7461/rules/orchestration.md) различает собственный блок работника и общие файлы, изменения которых применяет оркестратор. Это ещё не универсальный сериализатор и не программный интерфейс блокировок.

[Существующий валидатор](https://github.com/AlekseiChirkov/agentic-workflows/blob/8c2fa08c18115ffcf38a1798742c41e53a2c7461/scripts/validate-task.sh) проверяет часть структурных условий и возвращает ненулевой код при нарушениях. Он не доказывает полноту разбора, транзакционность записи либо законность всех переходов состояния.

## 2. Проблема и результат будущей работы

Свободное редактирование может создавать повторные блоки, терять обязательные поля, менять несвязанные разделы и перетирать параллельные изменения. Нужен небольшой детерминированный инструмент, который находит конкретный блок по идентификатору, меняет согласованные поля, проверяет переход и сохраняет результат целиком либо не меняет ничего.

Результат, если работа будет отдельно запланирована:

- один исполняемый файл на Python 3 со стандартной библиотекой в `ORCHESTRAIL_HOME/bin/`;
- интерфейсы `get`, `set`, `append-note`, `add-file`, `init-block`, `validate`;
- точное сохранение постороннего текста и неизвестных полей;
- согласованная блокировка каталога задачи и проверка ожидаемой ревизии;
- атомарная замена файла и восстановление после прерывания;
- необязательность инструмента во время исполнения и безопасная ручная процедура.

Точное имя исполняемого файла и минимальная поддерживаемая версия Python закрепляются при планировании реализации. Примеры ниже используют условное имя `state-tool`; это не установленная команда.

## 3. Границы владения

Инструмент владеет только разделом `## Subtask Progress` родительского `state.md`, включая блоки листовых и составных задач. Он не меняет `plan.md`, `.ai/memory/state.md`, описания задач, программный код, ветви, коммиты, статусы запросов на изменение и другие разделы `state.md`.

Вспомогательные технические файлы блокировки и временной записи допустимы только в разрешённом каталоге задачи и не становятся новым источником канонических статусов. Они не копируются в потребительский проект как обязательная инфраструктура; сам исполняемый файл остаётся в установленном корне проекта.

| Связанный документ | Граница |
|---|---|
| [14](14-task-context-and-reuse.md) | Создаёт производные представления контекста; не владеет изменением канонического состояния |
| [15](15-orchestrator-overhead.md) | Проверяет и формирует предложения; не получает произвольный интерфейс записи из-за существования этой спецификации |
| [12](12-composite-branch-model-and-parallel-children.md) | Может выполнять детей параллельно без этого инструмента, поскольку общие изменения применяет один оркестратор |
| [16](16-scoped-verification.md) | Определяет доказательства проверки; сериализатор не может самостоятельно объявить их успешными |
| [19](19-local-repair-and-escalation.md) | Определяет лимиты попыток; запись поля не обнуляет их |

Ни один из девяти потоков оптимизации не зависит от реализации 07. Возможное повторное использование проверенных схем из 15 — последующее решение, а не скрытая зависимость текущего плана.

## 4. Источники истины и совместимость

1. Формат блоков, словарь значений, обязательные и защищённые поля берутся из канонического контракта состояния на закреплённой ревизии. После переименований 13 используется новый единственный путь, а не вторая независимая копия грамматики.
2. Переходы и требуемые доказательства определяются соответствующими процессами выполнения и проверки. Из наличия значения в словаре не следует, что из любого состояния в него можно перейти.
3. Старый листовой блок без `atomic-tests:` читается как прежний формат с семантикой `not-started`; разбор выполняется по имени поля, а не его позиции. Это не доказательство пройденной фазы, и чтение не добавляет поле на диск. Если такой блок уже имеет `atomic-execution: in-progress`, каноническая совместимость запрещает требовать RED задним числом: уполномоченный писатель сохраняет в `notes:` точную запись `pre-TDD task, TDD step skipped` и продолжает разрешённый процесс. Команды `get`/`validate` лишь сообщают о применимости исключения, оставаясь читающими. Для новой или ещё не начатой задачи отсутствие поля не отменяет требуемые тесты.
4. Неизвестные поля сохраняются вместе со значениями, порядком и принадлежащими им строками. Неизвестное поле не объявляется ненужным и не удаляется при нормализации.
5. Неизвестный префикс блока обрабатывается согласно действующему правилу совместимости чтения, но запись в неоднозначно распознанную структуру запрещается до явного разрешения формата. Совместимость чтения не оправдывает рискованную сериализацию.
6. Состояние `atomic-tests: pinned` сохраняется как режим фиксации существующего поведения для изменений без изменения поведения: тесты проходят до изменения, а разрешённый следующий статус — только `green`. Нельзя превращать его в `red`, требовать искусственного отказа или применять к новой функции/исправлению поведения ради обхода RED. После появления `atomic-tests:` при выполнении тестового этапа поле не удаляется и не понижается для получения исключения старого формата.
7. Состояние `atomic-tests: n-a` допускается только с уже предусмотренным обоснованием уровня тестирования `none`; инструмент не выбирает этот уровень ради обхода тестов.
8. Ограничения ручного изменения не ослабляются. Если текущий процесс требует остановки при ошибке валидатора, историческое упоминание предупреждения не превращает её в необязательную проверку.

## 5. Нормативные требования

В исходной редакции требований с идентификаторами не было; REQ-01–REQ-14 введены для проверяемости.

- **REQ-01. Узкая область.** Изменять только выбранные поля конкретного блока внутри единственного целевого раздела. Весь остальной файл сохранять побайтно.
- **REQ-02. Структурный разбор.** Различать настоящие заголовки и примеры в ограждённых блоках кода, обнаруживать повторный раздел, повторный идентификатор, повреждённые отступы и неоднозначные границы. Не угадывать нужный блок по первому текстовому совпадению.
- **REQ-03. Каноническая сериализация.** Известные поля выводить в согласованном порядке; обязательные пустые поля сохранять. Неизвестные поля и защищённые строки не терять и не сокращать.
- **REQ-04. Проверка значений и переходов.** До записи проверять тип, словарь, допустимый переход и наличие требуемого доказательства. Недопустимый переход возвращает отказ без изменения файла. Проверка учитывает канонический путь `pinned → green`, законный `n-a` и точную совместимость старого уже начатого блока без ретроактивного RED.
- **REQ-05. Ожидаемая ревизия.** Каждая запись требует `expected_revision`, полученную при чтении. Ревизия охватывает весь исходный файл, чтобы не потерять чужие изменения за пределами выбранного блока. Несовпадение требует повторного чтения и нового предложения.
- **REQ-06. Блокировка.** Все записи сериализуются общей блокировкой каталога задачи; имя блокировки не зависит от идентификатора листа. Возраст блокировки сам по себе не доказывает смерть владельца и не даёт права её отобрать.
- **REQ-07. Атомарность.** Запись выполняется через проверенный временный файл на той же файловой системе и атомарную замену. Прерывание не оставляет частично записанный `state.md`. Требования долговечности данных после аварии питания явно отделяются от атомарности видимой замены.
- **REQ-08. Идемпотентность.** Повтор с тем же `operation_id` и теми же входами не создаёт второй блок, заметку или путь и не повторяет переход. Повторное использование идентификатора с другим содержимым означает конфликт.
- **REQ-09. Безопасные пути.** Путь задачи и файла разрешается внутри явно указанного корня; символьные ссылки и смена целевого файла не позволяют выйти за область. Значения полей являются данными и никогда не исполняются оболочкой.
- **REQ-10. Необязательность.** Отсутствующий инструмент допускает существующую ручную процедуру с записью причины в `notes:`. Неисправность инструмента не даёт права обходить живую блокировку, конфликт ревизии или запрещённый переход.
- **REQ-11. Честные результаты.** `get` и `validate` ничего не меняют. Успешная сериализация означает только допустимую запись; она не означает пройденные тесты, независимую проверку либо готовность задачи.
- **REQ-12. Восстановление.** После прерывания можно установить, применена ли операция, без повторного исполнения внешних действий. Остаточные временные файлы не принимаются за каноническое состояние.
- **REQ-13. Одна грамматика.** Инструмент, валидатор, генератор справочников и процессы используют согласованную версию контракта. Неизвестная новая версия, которую инструмент не умеет безопасно изменять, даёт отказ записи и сохраняет возможность читать исходный текст вручную.
- **REQ-14. Отдельное планирование.** Реализация начинается только после явного решения включить 07 в план; до этого документ остаётся проектом. Его детализация не меняет дорожную карту.

## 6. Проект интерфейса

Все операции принимают явно заданные каталог задачи и идентификатор блока. Для составной задачи тип блока проверяется по фактической структуре, а не по предположению вызывающей стороны.

| Команда | Вход | Результат и ограничения |
|---|---|---|
| `get` | Задача, блок; при необходимости конкретное поле | Значения, тип блока, версия схемы, `source_revision`; без записи и исправления формата |
| `set` | Поля и значения, `expected_revision`, `operation_id`, ссылки на доказательства | Одна атомарная проверенная группа связанных изменений; не произвольная замена всего раздела |
| `append-note` | Текст заметки, `expected_revision`, `operation_id` | Добавление без потери существующих заметок; повтор той же операции не дублируется |
| `add-file` | Конкретный относительный путь, `expected_revision`, `operation_id` | Добавление в `target_files:` по согласованным правилам; без выполнения `git add` |
| `init-block` | Идентификатор, тип, обязательные начальные поля, ожидаемая ревизия, идентификатор операции | Создание отсутствующего блока либо безопасный повтор; существующий прогресс не сбрасывается |
| `validate` | Задача, необязательный блок, версия контракта | Структурные и межполевые ошибки; без нормализации файла |

Составные изменения, для которых валидна только итоговая комбинация полей, передаются одним `set`. Несколько отдельных запусков `set` не считаются общей транзакцией. Инструмент не выполняет обновление `plan.md` после записи: согласование внешних артефактов остаётся обязанностью уполномоченного процесса.

Проект машинного результата:

```json
{
  "schema_version": 1,
  "operation_id": "op-example-001",
  "result": "applied",
  "task_id": "task-example",
  "block_id": "T-01",
  "source_revision": "sha256:<исходный-хэш>",
  "result_revision": "sha256:<итоговый-хэш>",
  "changed_fields": ["last_action"],
  "errors": []
}
```

Допустимые результаты: `applied`, `already_applied`, `unchanged`, `rejected`. Значение `applied` не является каноническим статусом задачи. Пример показывает будущую форму интерфейса и не является записью реального выполнения.

### 6.1. Коды завершения

Проект кода завершения должен быть стабилен и документирован при реализации:

| Код | Смысл |
|---|---|
| `0` | Успешное чтение/проверка/запись, неизменившийся результат либо доказанный безопасный повтор |
| `2` | Неверное обращение, неизвестная команда, отсутствующий обязательный аргумент |
| `3` | Повреждённая структура, неизвестная неподдерживаемая версия или неоднозначный блок |
| `4` | Конфликт ожидаемой ревизии |
| `5` | Живой/неясный владелец блокировки или истёкший срок ожидания |
| `6` | Недопустимое поле, значение, переход или недостаточное доказательство |
| `7` | Ошибка файловой операции, синхронизации или атомарной замены |
| `8` | Конфликт повторного `operation_id` |

Машинный ответ выходит отдельно от пользовательской диагностики. Возвращённый отказ нельзя считать успешным изменением из-за наличия частично сформированного вывода.

## 7. Блокировки и конкурентные изменения

### 7.1. Обязательные свойства

Взаимное исключение действует для всех процессов, которые могут пользоваться инструментом на одной задаче. Минимальные сведения о владельце: случайный идентификатор владения, идентификатор процесса с признаком его поколения, идентификатор машины/сеанса и время создания. Один номер процесса недостаточен: он может быть переиспользован.

Механизм выбирается на этапе планирования с учётом поддерживаемых файловых систем. Для локальной файловой системы предпочтителен механизм, автоматически освобождаемый операционной системой после завершения процесса. Если используется файл/каталог блокировки, необходим протокол проверки владельца и безопасного освобождения, а не только удаление старого файла.

Историческая идея «снять блокировку через десять минут» сохраняется как нерешённая политика, требующая согласования. Допустимая безопасная трактовка: десять минут дают повод проверить зависание и сообщить о нём. Они не разрешают автоматически вытеснить живого или непроверяемого владельца. Изменение ранее согласованной политики фиксируется решением при реализации.

### 7.2. Состояния владельца

| Наблюдение | Действие |
|---|---|
| Владелец доказанно активен | Ожидать в пределах явного срока либо вернуть отказ |
| Владелец доказанно завершён и запись относится к этому экземпляру | Восстановить владение по согласованной процедуре и записать диагностику |
| Нельзя проверить владельца, другую машину или файловую систему | Отказ автоматического захвата; сохранить данные |
| Имеется только большой возраст записи | Проверить владельца; не удалять по возрасту |
| Владелец сменился между проверкой и освобождением | Не удалять чужую блокировку; повторить процедуру |

Блокировка защищает только участников согласованного протокола. Произвольный внешний редактор может её не соблюдать. Проверка хэша перед заменой уменьшает риск, но сама по себе не является универсальной атомарной операцией сравнения и записи для любых внешних писателей. Поэтому ручной режим требует прекращения параллельной записи; документация не должна обещать более сильную гарантию.

## 8. Алгоритм безопасной записи

1. Разрешить корень задачи и файл, проверить допустимость пути и версию инструмента.
2. Получить блокировку каталога задачи, сохранив уникальное владение.
3. Прочитать исходный файл целиком и проверить отсутствие смены целевого файла.
4. Найти единственный целевой раздел и единственный блок. При повреждении остановиться без попытки автоматически исправить соседний текст.
5. Проверить долговечное подтверждение `operation_id` до требования совпадения старой ревизии: доказанно применённая операция с тем же содержимым возвращает `already_applied` без нового эффекта, даже если её первая запись уже изменила хэш файла. Противоречивый идентификатор означает конфликт. В ответе различаются историческая итоговая ревизия операции и текущая ревизия файла. Одного совпадения значения поля без подтверждения недостаточно.
6. Для новой операции проверить `expected_revision`; несовпадение означает отказ. Затем построить изменение в памяти. Проверить поля, переходы, доказательства, защищённые строки и обязательные пустые поля.
7. Сериализовать выбранный блок, сохранив остальные байты. Повторно разобрать кандидат и убедиться в сохранении инвариантов.
8. Записать кандидата во временный файл в том же каталоге; сохранить необходимые права доступа; выполнить предусмотренную синхронизацию данных.
9. Повторно убедиться, что источник и владение не изменились. При несовпадении удалить только собственный временный файл и вернуть конфликт.
10. Атомарно заменить целевой файл. При заявленной устойчивости к аварийному завершению синхронизировать каталог соответствующим поддерживаемой системе способом.
11. Вернуть итоговую ревизию и подтверждение операции. Освободить только собственную блокировку.

Ошибка до замены оставляет исходный файл. Прерывание после замены, но до ответа требует проверки идентификатора операции и итогового состояния; повтор не должен добавлять заметку дважды.

### 8.1. Долговечное подтверждение операции

Для идемпотентности `append-note` недостаточно временной памяти процесса. Идентификатор и хэш применённой операции должны сохраняться атомарно с изменяемым блоком. При планировании следует согласовать одно аддитивное защищённое поле, например `state-tool-receipts:`, в канонической грамматике.

Это поле хранит только технические подтверждения и не заменяет прогресс. Его формат, ограничение роста и правила удаления должны сохранять возможность безопасного повтора за заявленный период. Нельзя незаметно удалить подтверждения и обещать бесконечную идемпотентность. Пока расширение грамматики не принято, универсальная запись с долговечной идемпотентностью не считается готовой.

## 9. Ручной режим и восстановление

Отсутствие необязательного инструмента и отказ исправно работающего инструмента — разные случаи.

**При отсутствии инструмента:** уполномоченный агент прекращает конкурентную запись, читает весь целевой блок и защищённые условия, меняет только нужные поля, проверяет разницу и запускает существующий валидатор. В `notes:` сохраняется причина ручного изменения. Если блок повреждён и заметку невозможно безопасно добавить, сначала используется действующая процедура восстановления, а не создаётся ещё один конфликтующий блок.

**При конфликте или занятой блокировке:** ручной режим не используется для обхода отказа. Сначала устанавливаются актуальная ревизия, владелец и причина расхождения; затем строится новое предложение либо сохраняется остановка.

**После прерывания:** проверить канонический файл, последнюю подтверждённую операцию, временные файлы и живость владельца. Не копировать временный файл поверх состояния только потому, что его время новее. Не повторять тесты, коммиты или внешние действия по предположению, что ответ не был получен.

**При повреждении:** сохранить исходные байты для разбора, сообщить точное место и нарушенное условие, восстановить по подтверждённому последнему состоянию. Восстановление не удаляет новые доказательства, замечания и счётчики попыток.

## 10. Условия приёмки будущей реализации

Эти пункты проверяются после отдельного планирования, а не объявляются выполненными текущей редакцией документа.

- [ ] **AC-01** (REQ-01, REQ-02): листовой и составной блоки обнаруживаются корректно; примеры в ограждённом коде не принимаются за данные; повторные разделы/идентификаторы дают отказ.
- [ ] **AC-02** (REQ-03): после изменения сохраняются неизвестные поля, защищённые строки, обязательные пустые поля и все байты вне целевого блока.
- [ ] **AC-03** (REQ-04, REQ-13): незаконные значения и переходы отклоняются; законный `n-a` требует действующего обоснования; `pinned → green` допускается без искусственного RED, а незаконный переход из `pinned` отвергается; неподдерживаемая версия не перезаписывается.
- [ ] **AC-04** (REQ-05): два предложения к одной ревизии не могут оба без проверки перетереть друг друга; изменение соседнего раздела вызывает конфликт, а не потерю текста.
- [ ] **AC-05** (REQ-06): живой владелец старше десяти минут не вытесняется; мёртвый/неизвестный владелец, повторное использование номера процесса и смена владельца покрыты отдельными случаями.
- [ ] **AC-06** (REQ-07, REQ-12): прерывание до и после атомарной замены оставляет целый файл; временный файл не становится источником истины; после возобновления определим факт применения.
- [ ] **AC-07** (REQ-08): повтор `init-block`, `add-file`, `append-note` и `set` с одинаковым идентификатором безопасен; другой текст с тем же идентификатором отклоняется; перезапуск процесса не теряет подтверждение.
- [ ] **AC-08** (REQ-09): пути за пределами корня, опасные ссылки и подмена файла не вызывают запись; текст заметки с метасимволами остаётся данными.
- [ ] **AC-09** (REQ-10): отсутствие инструмента допускает описанное ручное выполнение; живая блокировка и конфликт ревизии не обходятся ручным переключателем.
- [ ] **AC-10** (REQ-11): чтение и проверка побайтно сохраняют все файлы; успешная запись не присваивает неподтверждённый статус проверки.
- [ ] **AC-11** (REQ-03, REQ-04, REQ-13): старый блок без `atomic-tests:` читается без записи и не считается прошедшим тесты. При уже существующем `atomic-execution: in-progress` разрешённое продолжение сохраняет точную заметку о старом формате без требования RED задним числом. Новая/не начатая задача не получает этого исключения; поле после выполненного тестового этапа нельзя удалить для обхода.
- [ ] **AC-12** (REQ-14): документация и граф зависимостей сохраняют статус отложенной работы; оптимизации 08 и 14–20 выполняются без установленного инструмента.

## 11. Порядок действий при отдельном планировании

1. Собрать реальные примеры повреждений и доказать полезность инструмента; не начинать реализацию только из-за наличия этой спецификации.
2. Закрепить текущую грамматику, её владельца, список защищённых полей и фактические места вызова `validate-task.sh`.
3. Разрешить вопросы блокировки, десятиминутной политики, подтверждений повторов и поддерживаемых файловых систем. Отдельно описать границу внешних редакторов.
4. Согласовать точный интерфейс и аддитивные поля с существующими читателями, генератором документации и ручной процедурой.
5. Подготовить отказные и аварийные проверки до реализации; затем реализовать разбор, проверку, запись и восстановление как отдельно проверяемые части.
6. Подключать к процессам постепенно, сохраняя ручной путь и все действующие обязательные остановки.

## 12. Открытые решения

Нужны только при включении работы в план: точный исполняемый файл и версия Python; поддерживаемые файловые системы; механизм блокировки; согласованная трактовка исторического срока; имя/схема/срок хранения подтверждений операций; режим миграции новых защищённых полей. Эти вопросы блокируют соответствующую будущую реализацию, но не текущие работы по другим спецификациям.
