# agentic_workflows — полный анализ проекта и сравнение с альтернативами

Redaction legend: Project A, Project B, and Project C are anonymized labels; the mapping is intentionally not recorded.

Дата анализа: 2026-09-16. Проанализировано 123 файла (≈16 000 строк markdown и shell):
38 workflow-файлов, 14 rules, 4 principles, шаблоны `.ai/`, 5 shell-скриптов,
`validate-contracts.sh` (534 проверки, все проходят) и 10 реальных run-логов из проектов
`Project A`, `Project B`, `Project C`.

---

## 1. Резюме

`agentic_workflows` — это не «набор промптов», а **спецификация SDLC-процесса для
LLM-агентов**, реализованная целиком на markdown и деплоящаяся в три среды (Claude Code,
Codex, Windsurf/Devin). Ядро системы: спека → Discovery (анализ, декомпозиция, дизайн) →
Execution (TDD-цикл на каждую подзадачу) → Validation (контракт, ревью, fix-задачи), при
этом всё состояние лежит на диске в `.ai/`, а не в контексте модели.

**Главная сильная сторона:** по глубине процессной инженерии система превосходит все
известные открытые аналоги — принудительный RED→GREEN с замороженным набором тестов,
разделение Implementer/Validator, класс A/B эскалаций с Арбитром, stacked-ветки с
восстановлением после squash-merge, машиночитаемый run-log и `/retro`, который его
анализирует. Ни один из сравниваемых фреймворков не покрывает эти пункты одновременно.

**Главная слабая сторона:** цена этой глубины. ~76 000 слов инструкций, 123 точки
остановки, 127 перекрёстных ссылок между файлами, отсутствие runtime — вся логика
исполняется «честностью» LLM, а логи показывают, что она регулярно нарушается (шаги
логируются задним числом с нулевой длительностью, вокабуляр статусов не соблюдается,
один subtask шёл 15 часов, агент был убит по лимиту расходов). Система спроектирована как
детерминированный конвейер, но исполняется недетерминированным интерпретатором.

**Для кого:** долгоживущие backend/infra-проекты (Python/FastAPI/Terraform) с одним-двумя
инженерами, которым важна ревьюируемость каждого изменения, аудит решений и повторяемость
процесса между несколькими AI-инструментами. **Не для:** прототипов, фронтенд-экспериментов,
команд без дисциплины поддержания `.ai/`, задач размером «поправить строку».

## 2. Что представляет собой проект

### 2.1 Архитектура

```
Источник истины (этот репозиторий)
├── rules/        14 файлов — всегда-активные контракты (workflow-globals, tdd, git-flow,
│                 orchestration, quick-flow, run-log, language + 5 phase-* bootstrap-правил)
├── principles/   4 файла — инженерные стандарты (code-quality, python, testing, infra)
├── workflows/    38 файлов — slash-команды: 3 фазовых оркестратора, 2 атомарных,
│                 19 дочерних шагов (pd-*, pe-*, pv-*, pae-*, pav-*), spec-run/restack,
│                 bugfix, spec-draft, spec-sync, adr-new, context-pack, retro, утилиты
├── templates/    .ai/ (скелет базы знаний проекта), .ai-umbrella/ (multi-repo), AGENTS.md
├── sync.sh       validate-contracts.sh → деплой в ~/.claude/skills, ~/.codex/skills,
│                 ~/.codeium/windsurf/global_*  + обход всех проектов с .devin/
├── setup-new-project.sh / setup-umbrella.sh — инициализация проекта
├── log-step.sh   append-only JSONL run-log с серверными timestamp'ами
└── logs/runs/    централизованная телеметрия всех запусков во всех проектах
```

### 2.2 Ключевые механизмы

| Механизм | Что делает | Где определён |
|---|---|---|
| **Состояние на диске** | `state.md` / `plan.md` / `T-XX/description.md` — единственный источник прогресса; «continue, never restart» | `workflow-globals`, `workflow-reference` |
| **Три фазы с жёсткими границами** | Discovery → Execution → Validation; авто-переход запрещён, кроме `/phase-pipeline` | `workflow-globals` |
| **TDD как контракт** | `/pae-tests` пишет падающие тесты из Acceptance Criteria, наблюдает RED, набор замораживается; `/pae-implement` не может ослабить тест; режим `pinned` для рефакторинга | `rules/tdd.md` |
| **Тест-левел гейт** | unit → integration → contract → smoke → none с обязательным обоснованием `none` | `rules/tdd.md` |
| **Flow tiers** | `quick` (≤3 файла, без инварианта, без изменения shipped-поведения, без миграции) vs `full` с mid-flight промоушеном | `rules/quick-flow.md` |
| **Автономный протокол решений** | 2–3 варианта, 5 линз (simplicity, reversibility, codebase fit, testability, blast radius), анти-overengineering фильтр, порог эскалации | `workflow-reference` |
| **Классификатор подзадач** | сигналы S1–S5, leaf / composite (Type 2) / vertical re-slice (Type 3), depth-2 cap, runtime tripwire для промоушена | `workflow-reference`, `pd-decompose` |
| **Оркестрация `/spec-run`** | 4 роли (Orchestrator, Arbiter, Implementer, Validator) как границы контекста; класс A (Арбитр с цитатой) vs класс B (только человек, batch-gate до первой ветки) | `rules/orchestration.md` |
| **Git-модель** | stacked-ветки по одной на подзадачу, `test:` + `feat:` коммиты как доказательство TDD, `base_commit` для `/restack` после любого merge-стратегии, запрет `git add -A`, никаких идентификаторов пайплайна в репозитории | `rules/git-flow.md` |
| **Run-log + retro** | пайплайны пишут JSONL через `log-step.sh`, `/retro` агрегирует через `jq` и предлагает изменения в самих workflow | `rules/run-log.md`, `retro.md` |
| **Contract validation** | 534 grep-проверки согласованности между файлами перед каждым деплоем | `validate-contracts.sh` |
| **Multi-repo** | umbrella `.ai/` + локальные `.ai/`, `working_dir:` в подзадачах | `setup-umbrella.sh`, `pd-decompose` |

`restarted`, `needs-work`; поле `gate` содержит произвольный текст.

## 4. Плюсы текущего проекта

1. **TDD не как пожелание, а как машина состояний.** `atomic-tests: not-started → red |
   pinned | n-a → green | failed`, RED требует *наблюдаемого* падения по правильной причине,
   тест, прошедший до реализации — это `failed`, а не успех. Режим `pinned` закрывает дыру,
   через которую рефакторинг обычно уходит от тестов. Это самая сильная и самая редкая часть.

2. **Разделение контекстов вместо ролевых «личностей».** Арбитр обязан цитировать источник
   («ответ без цитаты — не ответ, а вопрос человеку»); Validator не видит рассуждений
   Implementer. Это прямая инженерная защита от самоподтверждения модели, а не театр.

3. **Класс A / класс B и batch-gate.** Признание того, что в последовательной цепочке
   «отложить подзадачу = остановить всё», и вынос всех вопросов продуктового намерения в одну
   точку *до первой ветки* — зрелое проектное решение, которого нет ни у одного аналога.

4. **Git-модель под реальную работу с ревьюером.** `test:`-коммит как доказательство,
   `base_commit` как единственный вход для `/restack`, draft-PR до окончания валидации, запрет
   `git add -A` с объяснением *почему* (`.ai/` попадёт во все ветки). Правила читаются как
   post-mortem, а не как чеклист.

5. **Все состояние на диске, «continue, never restart».** Прерванный запуск возобновляется
   той же командой; Guard-секции защищают от перезаписи. По логам resume действительно
   работает (Project B: 4029e93a остановлен → 4305eda1 продолжен).

6. **Обратная связь на сам процесс.** Run-log с честными правилами («число, написанное
   моделью — догадка», «опущенное поле ≠ 0»), `/retro` с обязательной привязкой находки к
   конкретному файлу и правилом «не выдумывать находки». Это единственный из фреймворков,
   который пытается измерять себя.

7. **Quick-tier и `/bugfix` с явным гейтом.** Правила выросли из двух реальных инцидентов
   (23 директории `fix-NN` на однофайловые правки; ad-hoc фикс shipped-пайплайна без
   контракта) и оба задокументированы как worked examples. По логам bugfix-путь занимает
   3–21 мин и реально используется.

8. **Самодисциплина проекта.** Независимый аудит (20 находок, 4 blocker), спека фиксов,
   `AUDIT-PROMPT.md` для повторного аудита, 534 контрактных проверки, блокирующие деплой.
   Проект относится к себе как к продукту.

9. **Один источник — три среды + multi-repo.** `sync.sh` разрешает коллизии имён
   (`rule-` префикс), обходит все проекты, чистит локальные тени; umbrella `.ai/` решает
   задачу «где живёт архитектура взаимодействия сервисов».

10. **Отсутствие следов пайплайна в репозитории.** Ни `T-XX`, ни ADR-номеров, ни
    атрибуции в коммитах — репозиторий читаем для человека, никогда не видевшего систему.
    Компромисс (traceability только в untracked `state.md`) назван открыто.

## 5. Минусы текущего проекта

### 5.1 Структурные

1. **Нет runtime — всё исполняется добросовестностью модели.** 123 точки `**stop**`,
   Guard-секции, вокабуляры статусов, запреты на `git add -A` — всё это текст. Логи
   показывают, что модель его нарушает: 12 шагов с `duration 0` записаны одним пакетом
   *после* завершения (4305eda1), `outcome` принимает значения вне enum, `flow:` пустой в
   4 из 10 запусков. `log-step.sh` не валидирует вокабуляр, `validate-task.sh` не
   запускается автоматически. Система *описывает* детерминированный конвейер, но не
   *обеспечивает* его.

2. **Объём контекста.** 17 600 слов rules + 3 500 principles + до 4 200 слов на один
   workflow (`pd-select-model`) + бутстрап из 7 файлов `.ai/`. Одна атомарная итерация
   легко стартует с 40–60k токенов инструкций до того, как прочитан первый файл кода.
   `context-pack` смягчает только `.ai/`-часть. Для Windsurf/Codex, где always-on правила
   грузятся целиком, это ещё тяжелее. Часть «reference»-текста (rationale, worked examples,
   история инцидентов 2026-07-22) живёт в always-on файлах, хотя нужна раз в месяц.

3. **Стоимость и длительность не ограничены.** 26 и 21,7 часа на spec-run; 15 ч на одну
   подзадачу; 3 ч на `pd-select-model` (живой web-поиск каталога моделей *каждый* запуск по
   явному запрету кэшировать); Implementer «terminated by spend limit». Нет бюджета на
   подзадачу, нет таймаута, нет учёта токенов в run-log (поле `files` есть, `tokens`/`cost` —
   нет). `/retro` не может ответить на главный вопрос «сколько это стоит».

4. **Строгая последовательность.** Параллелизм запрещён из-за отсутствия блокировок в
   `## Subtask Progress`. Это честное ограничение, но оно означает, что 9 независимых
   подзадач идут 26 часов, тогда как Claude Code уже даёт worktrees и фоновые субагенты.
   Причина — выбранный формат состояния (один markdown-файл), а не природа задачи.

5. **Хрупкость перекрёстных ссылок.** 127 ссылок вида «см. `workflow-reference → ##
   Autonomous Decision Protocol`» между 56 файлами. Аудит нашёл 10 ссылок на несуществующие
   секции, дедлок `/phase-execution ↔ /phase-validation`, двойной триггер composite-validation.
   `validate-contracts.sh` — 1 400 строк grep'ов по подстрокам; он ловит удаление строки, но
   не смысловое расхождение. Каждое новое правило добавляет N проверок и M ссылок.

6. **Источник истины не под git.** Репозиторий `agentic_workflows` — `not a git
   repository`. Изменения в 76 000 слов контрактов нельзя откатить, сравнить, bisect'нуть;
   `/retro` предлагает менять workflow, но нет истории, чтобы связать изменение с эффектом
   в логах. Для проекта, требующего ADR на каждое решение, это противоречие.

### 5.2 Продуктовые

7. **Python/FastAPI/GCP-центричность.** `principles/python-standards.md`,
   `infra-standards.md`, единственный stack-шаблон `python-fastapi.md`, примеры с Alembic и
   Pydantic. Для TypeScript/Go/Rust/mobile придётся писать principles с нуля; тест-левел
   гейт и `testing-standards` (InMemory-репозитории, AAA) неявно предполагают clean
   architecture на бэкенде. Фронтенд, data science, ML-ноутбуки, игры — почти не покрыты.

8. **Порог входа и «второй пользователь».** USAGE.md — 774 строки; чтобы понять, почему
   `pav-propose --batch` означает «записать, ничего не применять», нужно прочитать три
   файла. Нет `examples/` с полным прогоном одной задачи (spec → state.md → plan.md →
   description.md → PR). Нет короткого «первые 15 минут». Система рассчитана на автора.

9. **Неравноценность сред.** Для Windsurf правила always-on, для Claude Code — skills
   (model-invoked), для Codex — только `AGENTS.md` + skills. Документ честно говорит, что
   семантика триггера меняется, и дублирует «essentials» в `global-claude.md`, но это
   значит, что в Claude Code полный контракт TDD загружается только если модель *решит*
   его загрузить. Субагентная оркестрация `/spec-run` (spawn, keep alive, message)
   вообще реализуема только в Claude Code; в Windsurf это фикция.

10. **Дублирование документации.** USAGE.md §7–9, PIPELINE.md, `workflow-reference`,
    описания в шапках каждого workflow — четыре места описывают одни и те же таблицы
    команд/статусов. Аудит уже находил рассинхрон; он будет повторяться.

11. **Спека — слабейшее звено без поддержки.** Шаблон `templates/spec.md` — 20 строк;
    `spec-draft` (3 500 слов) помогает, но нет нотации требований (EARS, Given/When/Then
    обязателен только в bugfix), нет чеклиста качества спеки как у Spec Kit, нет связи
    Acceptance Criteria ↔ тесты ↔ PR как проверяемого артефакта вне `notes:`.

12. **`pd-select-model` переусложнён.** 4 200 слов, 5-осевая оценка, обязательный живой
    web-поиск, специальные ветки для «creative» трейта — и 3 часа в реальном запуске. При
    этом реальная разница в цене между Sonnet/Opus на подзадачу известна заранее.

13. **Жёсткие абсолютные пути.** `~/projects/agentic_workflows`
    зашит в rules, workflows и `log-step.sh`; `--from` есть только у `sync.sh`. Перенос на
    другую машину/CI — ручная правка.

14. **Нет тестов для самих workflow.** Проверяется согласованность текста, но не
    поведение: нет «golden run» (фикстура spec → ожидаемые state.md/plan.md), нет
    регрессионного прогона после изменения правил. Аудит на 20 находок делался вручную
    через отдельный промпт.

## 6. Преимущества по сравнению с другими решениями

| Преимущество | Кому проигрывают |
|---|---|
| Единственная система с **принудительным, аудируемым TDD** (замороженный RED-набор, `pinned`, обоснованный `n-a`, отдельный `test:`-коммит как доказательство) | всем; Superpowers имеет TDD-скилл, но без гейта и статуса |
| **Независимая валидация** на трёх уровнях: атомарная (Validator без контекста), задачная (contract + review), интеграционная (composite) с генерацией fix-задач | BMAD (QA в том же контексте), Spec Kit/Kiro/OpenSpec (валидации нет) |
| **Git-модель под ревьюера**: stacked-ветки, draft→ready, `/restack` после любого merge, safety rails | никто из методологий не описывает git-слой; Superpowers даёт worktrees без стека |
| **Resume-контракт** с Guard'ами и reconcile git↔state | Conductor ближе всех, остальные — «перечитай файлы» |
| **Класс A/B эскалация + Арбитр с цитатами + batch-gate** — один запланированный стоп на всю задачу | все остальные либо спрашивают постоянно, либо не спрашивают вовсе |
| **Телеметрия и `/retro`** — процесс улучшается по данным, а не по ощущениям | ни у кого |
| **Quick-tier / bugfix** — губернированный путь для мелочи с формальным гейтом и mid-flight промоушеном | OpenSpec лёгкий целиком, остальные — либо всё, либо ничего |
| **Multi-repo umbrella** и `working_dir:` в подзадачах | ни у кого |
| **Один источник → 3 среды** с разрешением коллизий и обходом проектов | BMAD/Spec Kit/Agent OS тоже multi-tool, но без валидации перед деплоем |
| **Контрактная валидация и внешний аудит** самих инструкций | ни у кого |

Проигрывает конкурентам: по порогу входа (Spec Kit, OpenSpec, Superpowers), по
harness-enforcement (Kiro hooks, нативные hooks Claude Code), по параллельности
(Superpowers/worktrees), по размеру сообщества и экосистеме (BMAD, Spec Kit), по
нотации требований (Kiro EARS), по компактности контекста (все).

## 7. Для каких проектов подходят workflows

### Хорошо подходят

- **Долгоживущие backend-сервисы и data/infra-платформы** (Python/FastAPI, SQLAlchemy,
  Terraform, GCP) — principles написаны именно под них; логи показывают успешные прогоны на
  Terraform/dlt/CI-workflow задачах.
- **Проекты с 1–3 инженерами, где AI пишет большую часть кода, а человек ревьюит PR.**
  Stacked-ветки, `test:`-коммиты и тело PR с test evidence сделаны для этого сценария.
- **Multi-repo системы** с общей архитектурой (umbrella `.ai/`).
- **Legacy-кодовые базы**, где сначала нужен `/onboard-legacy-project`, а потом дисциплина
  «не менять shipped-поведение без контракта» (quick-flow условие 3).
- **Регулируемые/аудируемые домены** (финтех, платежи — судя по worked examples про
  NOWPayments и forex), где важно «почему приняли это решение» (ADR на каждое решение,
  `### Autonomous Decision` с оценками).
- **Задачи размера 3–8 подзадач по 3–15 шагов** — на это откалиброван декомпозер.
- **Команды, использующие несколько агентов** (Claude Code + Codex + Windsurf) и желающие
  один процесс для всех.

### Подходят с оговорками

- **TypeScript/Go/другой стек** — процессный слой универсален, но principles и
  тест-левел гейт нужно переписать; ожидайте 1–2 дня на адаптацию.
- **Фронтенд** — TDD-гейт по компонентам работает хуже; понадобятся правила для визуальных
  проверок и `smoke`-уровня через e2e.
- **Небольшие команды без выделенного «владельца процесса»** — `.ai/` протухает быстро,
  если никто не следит за `architecture.md` и ADR.

### Не подходят

- **Прототипы, хакатоны, эксперименты** — Discovery с 5-линзовой оценкой на одноразовый
  скрипт вредна.
- **Однострочные правки, если не через `/bugfix`** — полный путь на них избыточен даже в
  quick-tier.
- **Data science / ML-исследования** в ноутбуках — нет тестируемых Acceptance Criteria в
  нужном смысле.
- **Задачи с жёстким лимитом по времени/бюджету** — при текущем отсутствии бюджетов один
  spec-run может занять сутки и упереться в spend limit.
- **Работа только в Windsurf/Codex**, если нужен `/spec-run` — субагентная модель там
  не исполняется.

## 8. Что улучшить, чтобы разработка на этих workflows была качественной и эффективной

Отсортировано по соотношению эффект/усилие. Пункты 1–5 — быстрые, 6–10 — средние,
11–15 — стратегические.

### Быстрые (дни)

1. **Положить репозиторий под git.** Тегировать релизы контрактов; писать `contract_version:`
   в `state.md`, чтобы `/retro` мог связать изменение правил с изменением метрик. Без этого
   пункт 6 из `/retro` («какой шаг ухудшился») неразрешим.

2. **Валидировать вокабуляр в `log-step.sh`.** Отклонять (или нормализовать с
   предупреждением) `outcome`/`tests`/`promoted` вне enum, требовать `flow`. Сейчас 4 из 10
   логов невалидны для `/retro`, и метрики по ним — шум.

3. **Логирование через hooks, а не через промпт.** В Claude Code `PostToolUse`/`Stop`
   hooks могут вызывать `log-step.sh` автоматически с реальными timestamp'ами. Запуск
   4305eda1 (12 шагов по 0 с) показывает, что модель логирует пост-фактум; hook это
   исключает по конструкции.

4. **Кэшировать каталог моделей.** Файл с TTL 7 дней вместо живого web-поиска на каждый
   запуск; убрать 3 часа из `pd-select-model`. Сократить workflow до таблицы «тип
   подзадачи → tier» с override-колонкой.

5. **Бюджеты и таймауты на подзадачу.** Поля `budget_tokens:` / `max_wall_s:` в
   `plan.md`, проверка в `/spec-run` Step 4 перед spawn; превышение → `blocked` с записью,
   а не тихая смерть по spend limit. Записывать `tokens_in/out` и `cost_usd` в run-log
   (Claude Code отдаёт их в хуках и `--output-format json`).

### Средние (недели)

6. **Перенести enforcement из текста в harness.** Для Claude Code: `PreToolUse` hook,
   блокирующий `git add -A`, `git push` в base-ветку, `git reset --hard`, staging любого
   пути под `.ai/`; `deny`-правила в `settings.json`. Текст правил остаётся как объяснение,
   но нарушение становится невозможным, а не запрещённым. Аналогично — hook, который
   отказывает в редактировании файлов из RED-набора во время GREEN без записи
   `tdd: test amended` в `notes:`.

7. **Детерминированный state-tool.** Небольшой CLI (`state.py`/`state.sh`): `state get
   T-02 atomic-tests`, `state set T-02 last_action "..."`, `state validate`. Модель перестаёт
   редактировать markdown-блоки вручную; исчезает целый класс ошибок (усечённые блоки,
   потерянные `notes:`, дубли), а `validate-task.sh` вызывается на каждой записи. Это же
   открывает путь к блокировкам и параллельности (п. 11).

8. **Расслоить контекст по «горячести».** Разделить каждое правило на *contract* (2–3
   экрана, always-on) и *rationale* (worked examples, история инцидентов, таблицы примеров —
   on demand). Цель: атомарный шаг стартует с ≤15k токенов инструкций. `workflow-reference`
   (4 200 слов) и `PIPELINE.md` (2 700) кандидаты на «только по ссылке». Измерять
   фактический размер бутстрапа и писать его в run-log.

9. **Golden-run тесты для workflow.** Директория `tests/fixtures/<case>/` с spec + `.ai/`
   и ожидаемыми `state.md`/`plan.md`/`description.md`; прогон в `claude -p` (headless) с
   diff по нормализованным артефактам. Запускать перед `sync.sh` вместе с
   `validate-contracts.sh`. Три кейса покрывают 80%: flat, composite (Type 2), quick/bugfix.

10. **Единый источник для справочных таблиц.** Генерировать USAGE.md §7–10 и PIPELINE.md
    из front-matter workflow-файлов скриптом (`description:`, `invocation:`, `reads:`,
    `writes:`), а не поддерживать вручную четыре копии. `validate-contracts.sh` тогда
    проверяет front-matter, а не грепает прозу.

### Стратегические (месяцы)

11. **Параллельность для независимых подзадач.** После п. 7: один файл состояния на
    подзадачу (`T-XX/progress.md`) + агрегатор, git worktree на подзадачу, DAG из
    `Depends On`. Stacked-модель остаётся для зависимых цепочек; независимые ветки идут от
    base параллельно. 26-часовые запуски можно сократить в разы без потери контрактов.

12. **Стековые профили principles.** `principles/stacks/{python-fastapi,typescript-node,
    go,terraform,react}.md` с одинаковыми секциями и явной таблицей «тест-левел гейт для
    этого стека» (что считается unit/integration/contract/smoke в React-приложении).
    `setup-new-project.sh --stack=…` уже намекает на это, но реализован один профиль.

13. **Нотация требований и трассировка AC.** Обязательный Given/When/Then или EARS для
    Acceptance Criteria в спеке; чеклист качества спеки в `spec-draft` (как в Spec Kit);
    таблица `AC-N → test name → commit sha` как отдельная секция `state.md`, копируемая в
    тело PR. Сейчас связь живёт в `notes:` свободным текстом.

14. **Честная матрица сред.** Явно объявить Claude Code первичной средой (только там
    исполняются субагенты, hooks, worktrees), Codex — вторичной (AGENTS.md + skills, без
    `/spec-run`), Windsurf — «правила и одиночные шаги». Убрать из документации обещания,
    которые в среде не выполняются, и снять с `sync.sh` обязательство поддерживать
    семантику always-on там, где её нет.

15. **Онбординг и примеры.** `examples/oauth-task/` — полный прогон: спека, все артефакты
    Discovery, `state.md` после Execution, итоговый PR body, run-log. «Первые 15 минут»
    в README на 60 строк. `--dry-run` для `/phase-discovery` и `/bugfix`, не только для
    `/spec-run`. Это снижает порог входа — главный проигрыш Spec Kit/Superpowers.

### Дополнительно (малые, но полезные)

- Сделать корневой путь конфигурируемым через одну переменную (`AGENTIC_WORKFLOWS_HOME`),
  подставлять её в rules при `sync.sh`.
- Добавить в `pv-review` явный гейт на секреты/PII в диффе (сейчас «security» — один
  пункт списка без инструмента).
- `/retro` — писать отчёт также в машиночитаемом виде и хранить ряд метрик по версиям
  контрактов (для графика «стало лучше/хуже»).
- Дедуплицировать `rules/global-claude.md` и `templates/codex-global-AGENTS.md` —
  генерировать оба из одного источника.
- Убрать «шаг 2.5» и прочие дробные номера — они уже путают порядок (в логах
  `model-selection` встречается и до, и после batch-gate).

## 9. Итог

`agentic_workflows` — самая полная из известных открытых спецификаций AI-SDLC: там, где
BMAD даёт роли, Spec Kit — спеку и задачи, Superpowers — TDD-скилл и субагентов, Kiro —
hooks, здесь есть всё это разом плюс git-стек, валидационная фаза, resume-контракт и
телеметрия. Это её конкурентное преимущество и её главный риск: система на 76 000 слов
без runtime исполняется тем же вероятностным интерпретатором, которого она пытается
дисциплинировать, и логи показывают, что дисциплина держится не везде.

Наибольший прирост качества и эффективности даст не добавление новых правил, а
**перенос уже написанных правил в исполняемую форму**: git для источника истины,
state-tool вместо ручного редактирования markdown, hooks вместо запретов в прозе, бюджеты
и реальная телеметрия стоимости, golden-run тесты вместо grep-проверок. После этого
станет безопасно сокращать контекст и включать параллельность — две вещи, которые
сегодня делают каждую задачу дорогой и долгой.
